# CompeteAI

CompeteAI 是一个面向竞品分析场景的多 Agent 协作系统。它不是把“搜索、总结、写报告”塞进一次大模型调用里，而是把任务拆成可编排、可追踪、可质检、可沉淀记忆的完整工作流：用户提交分析需求后，系统会依次完成任务拆解、信息采集、结构化分析、报告生成、质量校验，并将结果以报告与 Trace 的形式返回给用户。

项目的核心目标不是做一个“能回答问题的聊天框”，而是构建一个适合真实业务场景的分析型 Agent 应用框架。对于竞品分析这类任务，真正重要的不是单次回答是否流畅，而是结论是否有来源、过程是否可回放、上下文是否能沉淀、系统是否能从单次 demo 演进为长期可扩展的平台。CompeteAI 的设计基本围绕这几个问题展开。

## 项目定位

在很多 AI 产品里，竞品分析通常被简化为一个 Prompt：给模型几个产品名，再让它输出 SWOT、功能表和建议。这种方式适合快速演示，但很难满足以下要求：

- 信息来源可追溯
- 任务过程可观测
- 输出结构稳定可复用
- 结果可被后续任务继续利用
- 系统可以平滑演进到异步、多节点、多 Agent 架构

CompeteAI 的定位正是解决这些问题。它将竞品分析视为一个多阶段、强上下文、强证据约束的任务流，而不是一次性的生成式回答。

## 核心能力

### 1. 多 Agent 协作分析

系统围绕竞品分析任务划分出五类核心 Agent：

- `Coordinator`：任务拆解、澄清判断、流程路由、全局状态协调
- `Collector`：联网搜索、网页抓取、资料整合、来源登记
- `Analyst`：功能对比、SWOT、定价、用户画像等结构化分析
- `Writer`：报告编排、章节生成、可视化数据整理
- `QA`：完整性检查、来源覆盖检查、质量评分、打回重做

这种拆分并不是为了“看起来更像多智能体”，而是为了把不同阶段的职责解耦开。采集、分析、写作、质检本身就是不同类型的认知任务，拆开以后更容易控制上下文、调优 Prompt、观察问题出在哪个阶段，也更方便后续引入独立 worker、异步消费和弹性扩容。

### 2. 面向证据的竞品报告

CompeteAI 的输出不是一段松散文本，而是一份结构化竞品报告。报告通常包含：

- 执行摘要
- 功能矩阵
- SWOT 分析
- 定价对比
- 用户画像
- 结论与建议

更重要的是，系统会尽量把结论和来源绑定起来。无论是 SWOT 中的优势判断，还是功能矩阵中的某一项对比，都会尽量附带 `sourceIds`，让前端能够把结论跳回原始资料。这种设计让报告从“像样”进一步升级为“可审阅、可复核、可追责”。

### 3. 可观测工作流与 Trace 回放

CompeteAI 将多 Agent 执行过程显式化为任务状态、事件流与 Trace 节点。用户不仅能看到最终报告，还能看到：

- 任务从创建到完成的完整状态变化
- 每个 Agent 的启动、执行、完成、失败、打回状态
- 阶段性输出、进度推进、错误信息
- 重试与打回闭环的回放信息

这种能力对于比赛答辩、产品演示、内部调试都很重要。它把一个原本隐藏在模型调用背后的黑盒过程拆开来，让系统真正具备“工程系统”而不是“提示词脚本”的质感。

### 4. 共享上下文与项目记忆

竞品分析任务不是孤立的。一次分析中的来源、结论、评分、摘要、产品画像，往往会在后续任务中继续有用。CompeteAI 在设计时把“记忆”作为一等能力对待，而不是临时补丁。

系统通过 Shared State / Blackboard 维护任务级共享上下文，并通过记忆服务沉淀长期可复用的信息，包括：

- 项目级显式规则，例如报告风格、术语、QA 门槛、来源偏好
- 任务级中间产物，例如采集材料、结构化分析结果、质检问题
- 完成态摘要，例如最终结论、质量评分、关键来源和阶段经验
- 可检索知识，例如事实、证据片段、向量化条目与语义召回结果

这使得 CompeteAI 更接近一个会不断积累项目知识的分析系统，而不是每次从零开始的临时助手。

## 设计原则

### 1. 先拆流程，再调模型

对于复杂任务，大模型能力当然重要，但更决定上限的是流程设计。CompeteAI 优先解决“任务如何拆、结果如何传、状态如何控、失败如何回滚、证据如何校验”这些结构问题，再在每个节点里引入模型能力。

### 2. 先保证结构稳定，再追求文本华丽

竞品分析的真正价值不在于措辞多漂亮，而在于结构是否稳定、字段是否完整、来源是否清晰、结果是否便于展示和复用。因此系统强调 JSON 化输出、协议化消息、前后端类型对齐和报告字段约束。

### 3. 先让系统可解释，再让系统更强

一个“看不见过程”的强模型，在真实工程里往往比不上一个“过程透明、证据充分、可回放”的中等模型系统。CompeteAI 将可解释性、可观测性、可回溯性作为核心工程特征来做，而不是演示层面的附加项。

### 4. 先把演示做成产品形态，再向平台演进

项目当前首先服务于竞品分析这一明确场景，但底层设计并没有把自己锁死在单一任务上。消息协议、事件总线、Shared State、Trace、记忆模块和 Agent 注册机制都具备继续抽象为通用分析 Agent 平台的潜力。

## 系统架构

从整体上看，CompeteAI 可以分为五层：

### 1. 前端交互层

前端基于 Vue 3 + TypeScript + Vite 构建，负责承载任务提交、报告展示、Trace 回放、Agent 能力视图和聊天式交互。界面不是传统营销页，而是面向工作场景的分析控制台。

这一层承担两个职责：

- 作为任务入口，接收分析需求、竞品列表和关注维度
- 作为结果出口，以结构化视图展示报告、来源和执行过程

### 2. API 与应用服务层

后端基于 Go + Gin 构建，负责提供任务、报告、Trace、聊天、记忆等接口，并通过 Wire 完成依赖注入。应用服务层对外暴露统一 API，对内协调任务仓储、工作流执行器、事件流、外部工具和记忆系统。

这一层的重点不是“写几个接口”，而是把任务型 AI 应用需要的状态管理、事件触发和服务边界处理清楚。

### 3. 工作流编排层

编排层是 CompeteAI 的核心。系统使用 Workflow Engine 统一管理任务生命周期、Agent 状态推进、打回闭环、重试逻辑、Trace 记录和事件广播。它既要像一个任务调度器，也要像一个流程控制器。

在这个层面，系统处理的问题包括：

- 任务从 `queued` 到 `completed` 的生命周期推进
- Agent 执行顺序与条件路由
- 失败、澄清、重做、取消等分支状态
- 报告与 Trace 的最终落库
- 对前端的 SSE 事件推送

### 4. 共享状态与记忆层

多 Agent 系统的本质难点不是“调多个模型”，而是“多个节点如何共享一致上下文”。CompeteAI 使用 Shared State / Blackboard 维护任务内共享信息，并用记忆模块维护跨任务的长期信息沉淀。

这一层负责保存：

- 任务元数据
- Agent 中间产物
- 报告草稿与最终稿
- QA 问题列表和评分
- 来源引用与证据目录
- 执行阶段日志和 Trace 节点

### 5. 基础设施与外部能力层

在基础设施层，CompeteAI 采用 MySQL、Redis、可选 Milvus、事件总线抽象与外部 MCP 工具体系支撑上层能力。这里并不是简单地堆技术名词，而是围绕任务型 Agent 应用的典型需求来选择组件：

- MySQL 负责持久化任务、报告、Trace、业务实体
- Redis 负责缓存、限流、共享状态与轻量运行态支撑
- Milvus 用于向量检索与可扩展记忆能力
- Firecrawl MCP 提供搜索、抓取与网页结构化能力
- Outbox 与 Bus 抽象支撑同步实现到异步架构的平滑过渡

## 端到端工作流

一个完整的竞品分析任务通常会按以下路径运行：

1. 用户在前端输入目标产品、竞品列表与分析维度。
2. `Coordinator` 对需求进行解析，必要时触发澄清。
3. `Collector` 通过 Firecrawl MCP 获取网页、文档与产品资料，并整理来源。
4. `Analyst` 基于采集结果生成结构化分析内容，包括 SWOT、功能矩阵、定价分析和用户画像。
5. `Writer` 将分析结果整合为最终报告结构，形成适合前端展示的内容。
6. `QA` 对报告进行字段完整性、来源覆盖率和质量得分检查。
7. 若 QA 发现问题，系统触发打回闭环，将任务路由回对应 Agent 重新处理。
8. 所有阶段完成后，系统保存报告与 Trace，并向前端推送完成事件。

这个流程的关键不在于顺序本身，而在于每一步都可以被单独观察、单独调优、单独替换，形成真正具备工程可演化性的任务流。

## 记忆系统设计

记忆系统是 CompeteAI 与普通报告生成 demo 最大的差别之一。项目将记忆拆成三个层次。

### 1. 显式记忆

显式记忆用于约束整个项目级别的规则，例如：

- 报告风格
- 分析维度偏好
- 常用术语映射
- 来源白名单与禁用表述
- QA 最低分阈值

它让系统在多次任务中保持稳定人格和输出规范，而不会因为单次 Prompt 变化导致风格飘忽。

### 2. 任务级工作记忆

每个任务执行过程中都会产生大量中间结果，这些结果既不能只存在某个局部变量里，也不能简单塞回一次模型对话。因此系统通过 Shared State / Blackboard 维护任务级工作记忆，供上游下游 Agent 随时读取。

这部分内容通常包括：

- 原始抓取结果
- 来源索引
- 分析草稿
- QA 问题
- 重做要求
- 最终报告结构

### 3. 可检索长期记忆

为了支持后续的复用、对比、相似分析与 RAG 化能力，系统还预留了长期可检索记忆层。其基本思路是把任务中的事实、证据、片段和总结转换成可查询的知识资产，并结合 Embedding 与向量索引进行召回。

这样做的意义在于：

- 下次分析相似产品时可以复用已有知识
- 可以逐步形成项目私有的竞品知识库
- 可为 QA、摘要、建议生成提供更稳定的背景信息

## Shared State / Blackboard 设计

如果说记忆系统回答的是“任务结束后留下些什么”，那么 Shared State / Blackboard 回答的是“任务执行时怎么共享上下文”。

在 CompeteAI 中，Blackboard 不是一个装饰性的概念，而是多 Agent 协作的事实中心。不同阶段的结果会被写入对应槽位，后续 Agent 不需要接收超长消息体，只需要读取共享状态即可。

典型内容包括：

- 任务基础信息
- 抓取材料与来源
- 结构化分析结果
- 报告草稿与最终报告
- QA 打分与问题清单
- Trace 事件与阶段节点

这种设计有几个直接收益：

- 降低 Agent 之间的直接耦合
- 减少上下文重复传输
- 方便 QA 横向检查多个阶段结果
- 方便前端直接消费阶段性结构化数据
- 方便未来切换到 Redis Blackboard 或跨进程状态存储

## 消息协议与异步演进

CompeteAI 从一开始就没有把系统写死为同步函数串联。虽然在工程落地上可以从单进程、内存总线起步，但协议和总线边界已经被提前抽象出来。

项目围绕任务创建、澄清、打回、完成、失败等事件定义统一消息语义，并将消息流、状态流和 Trace 流做了清晰划分。这样做的价值在于：

- 同一个任务可以同时驱动执行、展示和观测
- 同一套协议可以复用于本地执行器与未来 Kafka 驱动执行器
- 引入独立 worker 时不必推翻现有上层 API
- 打回、重试、回放等复杂流程可以建立在统一事件模型之上

从架构演进角度看，这是一种很有价值的做法。它允许项目先跑通业务，再逐步把底层执行模式替换为更强的消息驱动体系，而不必大规模重构领域接口。

## 来源追溯与 QA 机制

竞品分析最容易被质疑的点，是“这些判断从哪里来”。为了解决这一点，CompeteAI 把来源追溯和 QA 校验都做成了核心能力，而不是交付前临时补一段说明。

### 来源追溯

系统在采集阶段会整理来源目录，在分析阶段要求关键结论尽量绑定 `sourceIds`，在前端报告页中则以可点击方式展示来源引用。这样，用户看到的不只是一个结论，而是一条“结论 -> 证据 -> 原始资料”的完整链路。

### QA 机制

QA 节点重点检查以下问题：

- 报告字段是否完整
- SWOT、功能矩阵等核心内容是否覆盖到位
- 关键结论是否缺少来源支持
- 来源标识是否有效
- 报告质量是否达到门槛

当 QA 发现问题时，系统不会简单报错结束，而是可以将任务打回给相应 Agent 重做。这种闭环机制对竞品分析场景尤其重要，因为很多错误不是“系统崩了”，而是“结论站不住脚”。

## 技术选型

CompeteAI 的技术选型不是按流行度堆砌，而是围绕“多 Agent 工作流应用”的实际需求做出的组合。

### 前端

- Vue 3
- TypeScript
- Vite
- Vue Router
- Pinia
- Element Plus
- ECharts

选择这一组合，是因为它足够轻、足够快，同时也方便把报告页、任务页、Trace 页和状态视图做成一套统一的工作台式交互。

### 后端

- Go
- Gin
- GORM
- Google Wire
- Viper
- Zap

Go 适合构建这种任务状态明确、服务边界清晰、需要兼顾性能与工程约束的系统。Gin 与 GORM 提供成熟的 Web 和数据层能力，Wire 让依赖注入更清楚，Viper 与 Zap 让配置和日志具备更好的可维护性。

### 大模型与工具调用

- CloudWeGo Eino
- Doubao / Ark API
- Firecrawl MCP

Eino 提供了很适合 Go 技术栈的 Agent、工具与工作流编排能力；Doubao 负责核心推理；Firecrawl MCP 则补足联网搜索、抓取和内容转结构化文本的外部能力。这一组合让系统既有模型智能，也有真实数据入口。

### 状态、数据与检索

- MySQL
- Redis
- Milvus

MySQL 用于强持久化，Redis 用于运行态状态和轻量共享数据，Milvus 用于向量检索与记忆扩展。它们分别承担结构化数据、流程态上下文和可检索知识资产的不同职责。

### 事件与可观测

- SSE
- Event Log
- Outbox
- Bus / Router 抽象
- Trace 模型
- Prometheus 指标

这些选型共同服务于一个目标：让系统的执行过程可见、可回放、可统计、可扩展。

## 为什么不是单 Agent 方案

单 Agent 方案最大的问题不是“效果差”，而是系统边界混乱。一个节点既负责理解需求、又负责联网搜集、又负责比较推理、又负责写报告、又负责自我检查，最终会带来：

- 上下文过长
- 错误归因困难
- 输出结构不稳定
- 迭代调优成本高
- 无法形成真正有价值的 Trace

多 Agent 的价值，恰恰在于把复杂任务拆成清晰节点，并让每个节点都可以独立观测、独立治理、独立优化。对于竞品分析这种天然分阶段的任务，这种设计尤其合适。

## 快速开始

### 环境准备

建议准备以下基础能力：

- Go 1.26+
- Node.js 18+
- MySQL 8+
- Redis 5+
- 可选：Milvus、Kafka
- 可访问的大模型 API Key
- Firecrawl API Key

### 后端启动

项目默认通过配置文件和环境变量加载运行参数。准备好数据库、缓存和模型配置后，可直接启动：

```bash
go run . server
```

如果希望在本地开发时同时启动 API 与 Worker 逻辑，可使用：

```bash
go run . all
```

### 前端启动

```bash
cd frontend
npm install --legacy-peer-deps
npm run dev
```

开发环境下，前端会通过 `/api` 代理与后端交互，适合本地联调和任务流演示。

## 适用场景

虽然项目以竞品分析为核心场景，但其底层结构同样适合扩展到其他需要“多阶段分析 + 来源追溯 + 结果沉淀”的任务，例如：

- 行业研究
- 产品调研
- 市场信息汇总
- 招股书 / 财报摘要分析
- 技术方案对比
- 企业知识整编与问答增强

因此，CompeteAI 的意义并不只在于一个比赛题目，而在于它验证了一种适合分析型 Agent 应用的工程组织方式。

## 项目价值

CompeteAI 想解决的不是“模型能不能写一份报告”，而是“如何让一份 AI 报告具备工程可用性”。这背后对应的是四个价值判断：

- 结论要尽量带证据
- 流程要可以回放
- 上下文要能够沉淀
- 架构要支持持续演进

当一个系统同时具备这四点时，它就不再只是一个演示用的 AI 页面，而更接近真正能够进入业务流程的智能分析系统。CompeteAI 正是在朝这个方向构建。
