# 消息协议设计

## 1. 文档目标

本文档定义 CompeteAI 多 Agent 工作流中的统一消息协议，用于支撑以下场景：

- 本地串行执行器中的阶段流转
- 后续 Kafka Producer / Consumer 的消息传输
- Trace 与状态机的关联
- QA 打回与澄清循环

核心要求是：**协议先稳定，执行方式后替换**。先让本地流程和将来的 Kafka 流程复用同一套消息语义。

---

## 2. 落位目录

建议新增目录：

```text
internal/
├── protocol/
│   ├── messages.go
│   ├── types.go
│   └── artifacts.go
```

建议与现有模块关系：

- `internal/agent`
  - 消费与产出协议消息
- `internal/state`
  - 持久化消息对应的工件和阶段数据
- `internal/workflow`
  - 根据消息类型和状态决定路由
- `internal/repository`
  - 最终落库 Task / Report / Trace

---

## 3. 协议设计原则

### 3.1 统一信封

无论是任务创建、阶段完成、QA 打回还是澄清请求，外层都使用同一个消息信封结构。

### 3.2 轻消息，重数据

消息只传递控制流和必要元信息。大体量内容通过 Blackboard / Shared State 读取。

### 3.3 面向事件

每条消息都描述“发生了什么”，而不是“谁去调用某个函数”。

### 3.4 可追踪

每条消息都要能映射到一个 `task_id` 和一个 `trace_id`。

---

## 4. 顶层消息信封

建议在 `internal/protocol/messages.go` 定义：

```go
type MessageEnvelope struct {
    MessageID   string           `json:"message_id"`
    TaskID      string           `json:"task_id"`
    TraceID     string           `json:"trace_id"`
    FromAgent   string           `json:"from_agent"`
    ToAgent     string           `json:"to_agent"`
    MessageType MessageType      `json:"message_type"`
    Status      MessageStatus    `json:"status"`
    Payload     json.RawMessage  `json:"payload"`
    Artifacts   []ArtifactRef    `json:"artifacts,omitempty"`
    CreatedAt   string           `json:"created_at"`
}
```

字段说明：

- `MessageID`
  - 消息唯一标识
- `TaskID`
  - 所属任务
- `TraceID`
  - 所属流程追踪链
- `FromAgent`
  - 发送方 Agent
- `ToAgent`
  - 目标 Agent
- `MessageType`
  - 消息类型
- `Status`
  - 当前消息对应的处理状态
- `Payload`
  - 结构化业务载荷
- `Artifacts`
  - 本条消息关联的工件引用
- `CreatedAt`
  - 生成时间

---

## 5. MessageType 枚举

建议固定以下消息类型：

| 消息类型 | 发送方 | 接收方 | 含义 |
|---|---|---|---|
| `task_created` | API / TaskService | coordinator | 创建新任务 |
| `clarification_required` | coordinator | user/api | 请求用户补充信息 |
| `clarification_answered` | user/api | coordinator | 用户已答复澄清问题 |
| `plan_ready` | coordinator | collector | 已生成计划，进入采集 |
| `materials_ready` | collector | analyst | 采集素材已就绪 |
| `analysis_ready` | analyst | writer | 结构化分析已完成 |
| `report_ready` | writer | qa | 报告草稿已完成 |
| `qa_pass` | qa | workflow/router | 质检通过 |
| `qa_reject` | qa | coordinator/router | 质检打回 |
| `task_completed` | workflow/router | api/frontend | 任务完成 |
| `task_failed` | workflow/router | api/frontend | 任务失败 |

建议后续尽量不要随意新增类型，而是在已有类型的 `payload` 中扩展细节。

---

## 6. MessageStatus 枚举

建议在协议层固定以下状态：

```text
pending
running
completed
failed
rejected
```

说明：

- `pending`
  - 消息已创建，尚未被消费
- `running`
  - 正在处理对应阶段
- `completed`
  - 阶段处理成功
- `failed`
  - 阶段处理失败
- `rejected`
  - 被 QA 或路由器判定需重做

这套状态和 `domain.AgentRunStatus`、`domain.TaskStatus` 应保持语义映射，但不必完全同名。

## 7. Payload 类型设计

建议每个 `message_type` 对应一个清晰的 payload 结构。

## 7.1 TaskCreatedPayload

```go
type TaskCreatedPayload struct {
    Title       string   `json:"title"`
    Competitors []string `json:"competitors"`
    Dimensions  []string `json:"dimensions"`
}
```

## 7.2 ClarificationPayload

```go
type ClarificationPayload struct {
    Question string   `json:"question"`
    Options  []string `json:"options,omitempty"`
    Answer   string   `json:"answer,omitempty"`
}
```

说明：

- `clarification_required` 使用 `Question`
- `clarification_answered` 使用 `Answer`

## 7.3 PlanPayload

```go
type PlanPayload struct {
```

```go
type MaterialsPayload struct {
```

这里不应塞入全部页面内容，只放摘要和引用。

## 7.7 QAResultPayload

```go
type QAResultPayload struct {
```

- `pass`

## 8. Issue 结构

QA 打回时，问题对象必须结构化，便于前端展示与路由判断。

```go
type Issue struct {
    ID          string `json:"id"`
    Category    string `json:"category"`
    Location    string `json:"location"`
    Problem     string `json:"problem"`
    Suggestion  string `json:"suggestion"`
    Severity    string `json:"severity"`
}
```

推荐 `Category`：

- `source_missing`
- `analysis_incomplete`
- `pricing_missing`
- `report_structure`
- `unsupported_claim`

---

## 9. ArtifactRef 设计

大部分阶段数据应通过工件引用而不是直接塞进消息。

```go
type ArtifactRef struct {
    Type      string `json:"type"`
    Key       string `json:"key"`
    Version   int    `json:"version"`
    CreatedAt string `json:"created_at"`
}
```

推荐工件类型：

- `task_brief`
- `plan`
- `source_ref`
- `collected_material`
- `analysis_result`
- `report_draft`
- `qa_review`

推荐 `Key` 命名统一走 Blackboard 规则，例如：

- `task:{taskID}:workflow:plan`
- `task:{taskID}:collector:sources`
- `task:{taskID}:analysis:result`
- `task:{taskID}:report:draft`

---

## 10. 主流程消息流转

标准主流程如下：

```text
task_created
  -> coordinator
plan_ready
  -> collector
materials_ready
  -> analyst
analysis_ready
  -> writer
report_ready
  -> qa
qa_pass
  -> task_completed
```

若 QA 打回：

```text
report_ready
  -> qa
qa_reject
  -> coordinator/router
  -> target_agent
  -> ... 再次流转到 qa
```

---

## 11. 路由规则

建议初版使用固定路由规则表：

| 输入消息类型 | 默认接收方 | 下一跳 |
|---|---|---|
| `task_created` | `coordinator` | `collector` 或 `clarification_required` |
| `plan_ready` | `collector` | `analyst` |
| `materials_ready` | `analyst` | `writer` |
| `analysis_ready` | `writer` | `qa` |
| `report_ready` | `qa` | `qa_pass` 或 `qa_reject` |
| `qa_reject` | `coordinator/router` | `collector` / `analyst` / `writer` / `coordinator` |

---

## 12. 与 Blackboard 的配合方式

协议负责控制流，Blackboard 负责数据流。

### 12.1 消息中保留什么

- 阶段摘要
- 工件引用
- 路由信息
- 轻量元数据

### 12.2 消息中不要保留什么

- 大段网页正文
- 完整报告 JSON
- 大型来源数组全文

这样才能保证：

- 本地执行器更轻
- Kafka 版不受消息体膨胀影响

---

## 13. 与 Trace 的关系

每条消息至少映射到 2 个 Trace 动作：

1. 消息被创建
2. 消息被某 Agent 消费并处理

推荐 Trace 的最低粒度：

- `message.created`
- `agent.started`
- `agent.completed`
- `agent.failed`
- `qa.rejected`
- `task.completed`

消息信封中的 `TraceID` 必须贯穿整个任务生命周期。

---

## 14. 本地执行器与 Kafka 执行器的统一性

本协议应同时支持两种执行方式。

## 14.1 本地执行器

- 直接在内存中创建 `MessageEnvelope`
- 由流程引擎按顺序 dispatch 给下一个 Agent

## 14.2 Kafka 执行器

- `MessageEnvelope` 序列化后投递到对应 Topic
- Consumer 反序列化后再分发给 Agent

结论：**协议对象不因执行方式变化而变化。**

---

## 15. 版本演进建议

### v1

- 只支持单任务串行多 Agent
- 使用内存或 Redis Blackboard
- 使用固定消息路由

### v2

- 接 Kafka
- 增加重试、死信队列、回溯消费

### v3

- 引入更细粒度 QA Query / Response
- 增加更强的审计字段

---

## 16. 本文档产出的直接结论

实现时应保证：

1. 所有阶段都复用统一消息信封
2. `message_type` 固定、少而明确
3. 大数据不进消息体，只走 `ArtifactRef`
4. `task_id` 与 `trace_id` 全链路必带
5. QA 打回必须结构化表达问题与目标 Agent
