# CompeteAI 真实消息驱动企业架构蓝图

> 更新时间：2026-06-09  
> 目标读者：项目维护者、Cursor、后续工程实现者  
> 文档定位：**直接指导重构与实现**，不是概念说明文档

---

## 1. 目标

本方案的目标不是“把现有单进程工作流再包装得像分布式”，而是**将 CompeteAI 重构为一个真实消息驱动、支持跨实例部署、具备恢复和隔离能力的企业级多 Agent 平台**。

本文档默认采用最高标准，不讨论时间、人力、风险是否可控，只定义目标形态和实现路径。

目标能力如下：

1. **真实消息驱动**
   - Agent 之间只通过消息和共享状态协作
   - 不允许 API 进程直接调用 Agent 执行链
   - 不允许同一消息在发布时同步本地执行

2. **跨实例部署**
   - API、Worker、Recovery、Scheduler 进程可独立部署
   - 任意 Agent Worker 可水平扩容
   - 任意单实例故障不会导致整条任务链丢失

3. **恢复能力**
   - 消息未确认可重新认领
   - 任务执行中断后可自动恢复
   - Worker 崩溃后可从 Checkpoint 继续

4. **运行隔离**
   - API 只做接入和查询
   - Worker 只做消费和执行
   - Agent 按角色隔离、按 Topic 隔离、按资源隔离

5. **企业级可观测性**
   - 任务、消息、Agent、工具调用、状态迁移全链路可审计
   - 可追踪耗时、失败原因、重试次数、Token 成本、来源覆盖率

## 2. 当前系统与目标系统的本质差异

### 2.1 当前系统

当前系统的真实形态是：

- `TaskService.Create()` 创建任务后触发工作流
- `workflow.Engine` 负责调度、执行、状态推进、失败处理
- `TaskHub` 提供进程内 SSE 事件广播
- `MemoryBus` / `RedisStreamBus` 仍兼具“消息总线”和“本地执行入口”
- Blackboard 虽然抽象了，但仍可回落到内存实现

这意味着当前系统更接近：

**单进程工作流引擎 + 消息语义外壳**

而不是：

**真实消息驱动的分布式 Agent 平台**

### 2.2 目标系统

目标系统必须满足：

- API 进程不执行 Agent
- 消息发布只负责写入总线
- Worker 消费后才执行 Agent
- 成功后 ACK，失败后重试或进入死信
- 任务恢复依赖持久化状态，不依赖进程内存
- SSE 从持久化事件流读取，不依赖本机 channel

### 3.2 进程职责边界

#### API Server

只负责：

- 创建任务
- 查询任务 / 报告 / Trace
- 接收用户澄清
- 提供 SSE / WebSocket 订阅
- 鉴权、限流、审计

禁止：

- 启动 Worker
- 执行 Agent
- 推进工作流状态

#### Worker

只负责：

- 消费分配给自身角色的 Topic
- 读取 Blackboard
- 执行 Agent
- 写回产物、Trace、事件
- 产出下一条消息

#### Recovery / Orchestrator

只负责：

- 扫描长时间未推进任务
- 处理超时 lease
- 重新认领未 ACK 消息
- 将异常任务转为 retry / dead-letter / failed

#### Scheduler

可选，负责：

- 定时巡检
- 清理过期状态
- 统计聚合
- 周期性评估模型与工具健康度

## 5. 消息模型

### 5.1 基本原则

1. **命令和事件分离**
2. **轻消息，重状态**
3. **消息天然可重放**
4. **消息处理必须幂等**
5. **成功提交下一消息之前不得 ACK 当前消息**

### 5.2 Topic 设计

建议采用下列 Topic：

```text
task.command.create
task.command.cancel
task.command.clarify

agent.command.coordinator
agent.command.collector
agent.command.analyst
agent.command.writer
agent.command.qa

agent.query.qa_to_analyst
agent.reply.analyst_to_qa

task.event.lifecycle
task.event.progress
task.event.trace
task.event.audit

task.dlq.coordinator
task.dlq.collector
task.dlq.analyst
task.dlq.writer
task.dlq.qa
```

如果使用 Kafka，建议每个 `agent.command.*` 独立分区策略：

- 分区键：`task_id`
- 同一任务消息固定进入同一分区
- 保障单任务有序

### 5.3 消息信封

```go
type Envelope struct {
    MessageID       string          `json:"message_id"`
    CorrelationID   string          `json:"correlation_id"`
    CausationID     string          `json:"causation_id"`
    TaskID          string          `json:"task_id"`
    TraceID         string          `json:"trace_id"`
    AggregateID     string          `json:"aggregate_id"`
    Topic           string          `json:"topic"`
    Kind            string          `json:"kind"`            // command | event | query | reply
    Name            string          `json:"name"`            // agent.run.request ...
    From            string          `json:"from"`
    To              string          `json:"to"`
    Attempt         int             `json:"attempt"`
    Priority        int             `json:"priority"`
    DedupKey        string          `json:"dedup_key"`
    SchemaVersion   int             `json:"schema_version"`
    Payload         json.RawMessage `json:"payload"`
    Artifacts       []ArtifactRef   `json:"artifacts,omitempty"`
    Metadata        map[string]any  `json:"metadata,omitempty"`
    OccurredAt      string          `json:"occurred_at"`
}
```

新增字段必须至少包含：

- `CorrelationID`：整条业务链路 ID
- `CausationID`：由哪条消息触发
- `DedupKey`：幂等键
- `Attempt`：重试次数
- `SchemaVersion`：消息版本

### 5.4 命令与事件命名

推荐命名：

#### Command

- `task.create.request`
- `task.cancel.request`
- `task.clarify.submit`
- `agent.run.request`
- `qa.query.request`

#### Event

- `task.created`
- `task.started`
- `task.progress.updated`
- `agent.started`
- `agent.completed`
- `agent.failed`
- `qa.rejected`
- `qa.passed`
- `task.completed`
- `task.failed`
- `task.cancelled`

#### Reply

- `qa.query.answered`

### 5.5 ACK 规则

严格执行：

1. 收到消息
2. 检查幂等
3. 获取 lease
4. 执行业务
5. 写 Blackboard
6. 写 Trace / Event / Audit
7. 发布下一条消息
8. 提交 checkpoint
9. **最后 ACK 当前消息**

任何步骤失败：

- 不 ACK
- 进入 retry
- 超过阈值后进入 DLQ

## 6. 共享状态模型

### 6.1 Redis 作为唯一运行态共享存储

生产模式下不允许内存 Blackboard。

运行态共享状态全部进入 Redis：

- `task:{id}:task:meta`
- `task:{id}:task:status`
- `task:{id}:workflow:state`
- `task:{id}:workflow:checkpoint`
- `task:{id}:workflow:lease`
- `task:{id}:collector:*`
- `task:{id}:analysis:*`
- `task:{id}:report:*`
- `task:{id}:qa:*`
- `task:{id}:events:cursor`

### 6.2 Checkpoint 结构

```go
type TaskCheckpoint struct {
    TaskID             string   `json:"task_id"`
    TraceID            string   `json:"trace_id"`
    CurrentAgent       string   `json:"current_agent"`
    CurrentMessageID   string   `json:"current_message_id"`
    LastCompletedStep  string   `json:"last_completed_step"`
    LastPublishedTopic string   `json:"last_published_topic"`
    Round              int      `json:"round"`
    RetryCount         int      `json:"retry_count"`
    RejectionCount     int      `json:"rejection_count"`
    ClarificationOpen  bool     `json:"clarification_open"`
    WaitingOn          string   `json:"waiting_on"`
    LeaseOwner         string   `json:"lease_owner"`
    LeaseExpireAt      string   `json:"lease_expire_at"`
    UpdatedAt          string   `json:"updated_at"`
}
```

### 6.3 Lease 机制

每条任务在某一时刻只允许一个 Worker 对当前阶段持有有效 lease。

建议：

- key：`lease:task:{taskID}:{agent}`
- value：`worker_instance_id`
- TTL：30s
- Worker 每 10s heartbeat 一次
- lease 失效后可被 recovery 或其他 worker 重新认领

### 6.4 历史保留

不能只保留最新值。

必须支持：

- `qa:history`
- `analysis:result:v{n}`
- `report:draft:v{n}`
- `collector:sources:v{n}`

要求：

- 当前版本走固定 key
- 历史版本走版本化 key 或 list/set 索引

## 8. Worker 模型

### 8.1 Worker 角色

Worker 必须按角色启动：

```text
WORKER_ROLE=coordinator
WORKER_ROLE=collector
WORKER_ROLE=analyst
WORKER_ROLE=writer
WORKER_ROLE=qa
```

每个角色只订阅自己的 Topic。

### 8.2 Worker 生命周期

```text
启动
  -> 注册角色处理器
  -> 加载配置
  -> 连接 Redis / DB / Bus
  -> 启动 consumer
  -> 获取消息
  -> 幂等检查
  -> 获取 lease
  -> 处理
  -> 发布后继消息
  -> ACK
  -> 上报 metrics / event
  -> 等待下一条
```

### 8.3 幂等机制

每条消息必须做幂等：

- key：`dedup:{messageID}` 或 `dedup:{dedupKey}`
- TTL：至少 7 天

若检测到已处理：

- 直接 ACK
- 不再重复执行 Agent

### 8.4 重试策略

建议：

- 最多重试 `5` 次
- 间隔采用指数退避：`5s, 15s, 30s, 60s, 120s`
- 区分错误类型：
  - 工具暂时失败：可重试
  - 模型超时：可重试
  - JSON 解析失败：可重试有限次
  - 业务校验失败：不可重试，直接失败或打回

### 8.5 DLQ 策略

超过最大重试次数：

- 消息转入 `task.dlq.{agent}`
- 记录 `dead_letters`
- 将任务状态更新为 `failed` 或 `attention_required`

## 9. Orchestrator 与 Router

### 9.1 职责

`orchestrator` 不执行 Agent 逻辑，只负责：

- 解析消息语义
- 维护任务状态机
- 决定下一跳
- 协调 rework / clarification / cancellation
- 管理 checkpoint

### 9.2 状态机

任务状态建议定义为：

```text
pending
queued
running
clarifying
reworking
waiting_reply
completed
failed
cancelled
attention_required
```

### 9.3 Agent 状态

```text
pending
leased
running
completed
failed
retrying
rejected
skipped
timed_out
```

### 9.4 路由规则

基础主链：

```text
task.create.request
  -> coordinator
coordinator completed
  -> collector
collector completed
  -> analyst
analyst completed
  -> writer
writer completed
  -> qa
qa passed
  -> task.completed
qa rejected
  -> coordinator / target agent
```

高级规则：

- QA 先发 query，再决定 reject
- Clarification 打开后任务挂起
- Cancel 消息优先级最高
- 同一任务同一阶段仅允许一个活跃 command

## 10. QA 局部返工模型

这是企业架构里必须实现的协作能力，不应只支持整链重跑。

### 10.1 交互链

```text
QA -> qa.query.request -> Analyst
Analyst -> qa.query.answered -> QA
QA:
  if satisfied -> qa.passed
  else -> qa.rejected(target=analyst or writer or collector)
```

### 10.2 返工粒度

必须支持：

- 只补来源
- 只修 SWOT 一项
- 只重写摘要段落
- 只补定价信息

实现手段：

- 在 Blackboard 保存 `review_notes`
- Writer / Analyst 支持 section-level rewrite
- QA issue 中明确 `location`、`target_agent`、`required_action`

## 11. 事件流与前端订阅

### 11.1 禁止使用进程内 `TaskHub` 作为生产 SSE 来源

生产模式下，SSE 必须读取持久化事件流。

两种可选模式：

#### 模式 A：DB Event Log + Polling Cursor

- Worker 写 `event_logs`
- API SSE 按 `sequence_no` 或 `id` 读取增量事件

#### 模式 B：Redis Stream Event Bus

- Worker 写 `task.event.*`
- API 为每个连接维护 cursor

建议：

- **主存档用 DB**
- **实时推送用 Redis Stream**

### 11.2 前端可消费事件

建议统一事件：

- `task_created`
- `task_started`
- `task_status`
- `agent_started`
- `agent_progress`
- `agent_completed`
- `agent_failed`
- `tool_call_started`
- `tool_call_completed`
- `qa_query`
- `qa_rejected`
- `clarification_required`
- `task_completed`
- `task_failed`

## 12. 恢复机制

### 12.1 消息恢复

对于 Redis Stream：

- 周期性扫描 pending list
- 使用 `XAUTOCLAIM` 认领超时消息

对于 Kafka：

- 依赖 consumer group offset
- 使用手动提交 offset
- 未提交消息自动重新消费

### 12.2 任务恢复

Recovery 进程定时扫描：

- `tasks.status in (running, reworking, waiting_reply)`
- `checkpoint.updated_at` 过久未变更
- `lease` 已过期

恢复动作：

1. 判断当前阶段
2. 若有未完成消息，则重新入队
3. 若无消息但 checkpoint 未完成，则生成补偿消息
4. 若超时过久，则转为 `attention_required`

### 12.3 Worker 恢复

Worker 启动时：

- 注册 consumer
- 获取角色订阅
- 不需要扫描全量任务

恢复由独立 Recovery 组件负责，不应让 Worker 自己全盘恢复。

## 15. 实施顺序

下面是推荐给 Cursor 的硬性实施顺序，不要跳步。

### Phase 1：进程拆分

1. 新建 `cmd/api`
2. 新建 `cmd/worker`
3. 新建 `cmd/recovery`
4. API 中删除任何 `engine.Start()` 逻辑
5. Worker 进程按 `WORKER_ROLE` 启动

验收：

- API 启动后不会执行任务
- Worker 不启动时任务只会停留在 queued

### Phase 2：总线语义修正

1. 重写 Bus 接口，区分 `Publish`、`Consume`、`Ack`、`Nack`
2. 删除 publish 时的本地同步 dispatch
3. 支持手动 ACK
4. 支持 retry 和 DLQ

验收：

- 消息未 ACK 时 Worker 重启后仍可重新处理

### Phase 3：共享状态与 Checkpoint

1. 生产模式强制 Redis Blackboard
2. 落地 `task_checkpoints`
3. 引入 lease
4. 引入状态历史版本

验收：

- Worker 崩溃后可根据 checkpoint 恢复

### Phase 4：角色化 Worker

1. 拆 Coordinator / Collector / Analyst / Writer / QA handlers
2. 每个 handler 只消费自己的 topic
3. Router 独立为 orchestrator 逻辑

验收：

- 可只启动某一类 worker
- 可对 Analyst 单独扩容

### Phase 5：事件流与 SSE

1. 引入 `event_logs`
2. API SSE 改读持久化事件源
3. 删除生产模式下 `TaskHub` 依赖

验收：

- API 重启后前端仍能继续看到任务事件流

### Phase 6：恢复与运维能力

1. recovery 进程扫描超时任务
2. pending message reclaim
3. 死信记录与重放接口
4. 管理端查看卡死任务

验收：

- 人工 kill 掉 worker 后任务仍可恢复推进

### Phase 7：高级协作

1. QA query / response 完整闭环
2. section-level rewrite
3. 可选择局部返工

验收：

- QA 可只打回一个 claim，不触发整链重跑

## 16. Cursor 实施要求

交给 Cursor 时，明确要求如下：

1. **不要在旧 `workflow.Engine` 上继续堆逻辑**
   - 允许复用已有 domain / agent / repository
   - 不允许继续把执行、调度、SSE、恢复糊在一个结构里

2. **优先拆边界，再补功能**
   - 先拆进程和模块
   - 再补消息 ACK、恢复、DLQ
   - 最后补前端 SSE 适配

3. **每一步都要可运行**
   - 先交付 API-only
   - 再交付 single-role worker
   - 再交付 recovery

4. **不要保留“内存模式可直接跑生产路径”的默认值**
   - dev 可以有 fallback
   - prod 绝不能 fallback 到内存总线或内存 blackboard

5. **每个阶段必须补测试**
   - bus ack/retry 测试
   - checkpoint 恢复测试
   - lease 争抢测试
   - role-based worker 集成测试

## 17. 最终验收标准

只有满足以下条件，才能宣称已经完成“真实消息驱动企业架构”：

1. API、Worker、Recovery 三类进程已经拆分
2. Agent 通过消息协作，不再通过进程内调用推进
3. 消息具有 ACK / Retry / DLQ / Idempotency
4. Blackboard 生产模式完全基于 Redis
5. SSE 基于持久化事件流，不依赖本地内存广播
6. Worker 崩溃后任务能够自动恢复
7. 同一角色可多实例横向扩容
8. QA 可执行局部返工和局部追问
9. 任务、消息、事件、checkpoint、lease 均可审计
10. 前端可稳定展示真实运行态，而不是推测态

---

## 18. 结论

这份方案的核心不是“把现有项目改得更复杂”，而是：

**把系统从单进程工作流引擎，升级为真正的消息驱动协作平台。**

真正的分水岭只有几个：

- API 不执行
- Publish 不本地执行
- Worker 有 ACK 和恢复
- 共享状态不在内存
- 事件流不在内存

只要这几个点落地，CompeteAI 才能从“像多 Agent”进入“真多 Agent”的工程阶段。
