# 项目记忆

更新时间：2026-06-04

## 1. 项目定位

CompeteAI 是一个面向竞品分析场景的多智能体协作系统。目标链路是：

用户创建任务 -> Coordinator 拆解 -> Collector 采集 -> Analyst 分析 -> Writer 成文 -> QA 质检 -> 前端查看报告与 Trace

项目技术栈以 Go 后端 + Vue 3 前端为主，辅以 Redis、MySQL、Eino、Firecrawl MCP，并在设计上预留 Kafka 异步通信与 Shared State / Blackboard。

## 2. 当前实现的真实状态

### 2.1 已经落地

- 后端已有完整的任务主链路：
  - `POST /api/tasks`
  - `GET /api/tasks`
  - `GET /api/tasks/:id`
  - `GET /api/tasks/:id/stream`
  - `POST /api/tasks/:id/clarify`
  - `GET /api/reports/:taskId`
  - `GET /api/traces/:taskId`
- 已实现 5 个 Agent 的统一接口与注册表：
  - `internal/agent/agent.go`
  - `internal/agent/registry.go`
  - `internal/agent/coordinator.go`
  - `internal/agent/collector.go`
  - `internal/agent/analyst.go`
  - `internal/agent/writer.go`
  - `internal/agent/qa.go`
- 已实现工作流执行器：
  - `internal/workflow/engine.go`
  - 支持任务运行、QA 打回、澄清、取消、SSE 进度推送
- 已实现 Blackboard 抽象与 TaskStore：
  - `internal/state/blackboard.go`
  - `internal/state/redis.go`
  - `internal/state/task_board.go`
- 已实现任务/报告/Trace 持久化：
  - `internal/repository/analysis.go`
  - `internal/repository/dao/task.go`
  - `internal/repository/dao/report.go`
  - `internal/repository/dao/trace.go`
- 已实现前端任务、报告、Trace、Agents 页面基础能力。

### 2.2 当前不是“真正分布式多智能体”

虽然代码里有 Agent、Router、Bus、Topic、Blackboard 这些概念，但现在的真实运行形态仍然是：

- `taskService.Create()` 起 goroutine 直接调用 `engine.Run()`
- `engine.Run()` 在单进程内按固定顺序串行执行 5 个 Agent
- Agent 之间的“消息”主要用于记录和审计，不是实际调度入口

关键文件：

- `internal/service/task_service.go`
- `internal/workflow/engine.go`

因此，当前更准确的描述是：

**单进程、多角色、可打回的工作流系统**

而不是：

**基于消息驱动的分布式多智能体系统**

## 3. 架构判断

### 3.1 已有骨架

项目已经具备以下多智能体骨架：

- 统一 Agent 接口
- Agent Card / 能力展示
- 工作流状态机
- QA 打回闭环
- Clarification 澄清闭环
- Shared State / Blackboard 抽象
- Protocol / MessageEnvelope / ArtifactRef
- Kafka Topic 和 Router 抽象
- SSE 事件推送与 Trace 持久化

这些基础是成立的，说明项目不是 demo 拼接，而是已经进入“可演化”为完整多智能体架构的中间状态。

### 3.2 主要缺口

当前离目标架构还差这些关键层：

1. 真正的消息驱动执行
- 现在没有每个 Agent 的独立 consumer / worker
- Topic 没有驱动 Agent 执行，只做日志路由
- `ioc/kafka.go` 里即使开启 Kafka，也还是 `MemoryBus` fallback

2. 运行态隔离
- 5 个 Agent 都在同一进程内运行
- 无法独立扩缩容
- 无法按 Agent 维度做资源隔离

3. 进程内状态过多
- `clarifyCh` 和 `runCancel` 在 `Engine` 内存中
- `TaskHub` 也是单进程内存事件中心
- 多实例部署后，澄清、取消、事件广播都不可靠

4. Blackboard 默认没有真正跨进程共享
- 虽然支持 Redis Blackboard
- 但 `config/dev.yaml` 里 `use_redis_blackboard: false`
- 默认仍是内存 Blackboard

5. Agent-to-Agent 高级交互未落地
- 文档设计了 `qa.query` / `analyst.response`
- 代码只定义了 topic，没有实现真实消费链路
- QA 目前只有“整段打回”，没有“局部追问”

6. 个别 Agent 仍偏轻
- Analyst 是当前最像“智能 Agent”的节点
- Writer 主要是合成已有结构化结果
- QA 主要是规则校验，不是工具型事实核验

## 4. 对各 Agent 的当前理解

### Coordinator

职责：
- 校验任务元信息
- 生成 workflow plan
- 处理 clarification answer
- 接收 QA 打回并决定重跑起点

特点：
- 更像状态协调器和路由器
- 目前没有 LLM 参与

### Collector

职责：
- 用 Firecrawl 做 search / scrape
- 整理 sources、materials、summary
- 写入 Blackboard 供下游读取

特点：
- 已接入真实工具链
- 但抽取/校验还比较轻，距离设计文档中的五阶段 Collector 还有差距

### Analyst

职责：
- 读取 Collector 结果
- 调用 LLM 输出严格 JSON
- 生成 SWOT、功能矩阵、定价、用户画像

特点：
- 当前最核心的智能节点
- 也是系统结果质量最敏感的地方

### Writer

职责：
- 读取分析结果
- 组装 report draft 和 report final

特点：
- 当前更接近“汇编器”
- 还不是独立写作 Agent

### QA

职责：
- 检查 summary、SWOT 覆盖、feature 数量、sources 存在性
- 按规则得分
- 失败时定位打回给 Collector / Analyst / Writer

特点：
- 已形成闭环
- 但仍偏规则校验，不是证据驱动的审稿 Agent

## 5. 当前最关键的事实

- 项目已经不是“只有文档没有实现”
- 但也还没有达到“真正分布式多智能体”
- 现阶段最准确的工程定位应该是：

**MVP 已有，架构骨架齐全，执行模型仍是单机编排**

## 7. 建议的后续优先级

### P0

把“多智能体骨架”升级为“真实消息驱动架构”：

1. 每个 Agent 独立 consumer 化
2. Kafka 真接入，不再只用 `MemoryBus`
3. Redis Blackboard 默认启用
4. clarification / cancel / SSE 事件从进程内存迁到跨实例可用方案

### P1

增强 Agent 自治性：

1. Writer 增加独立写作/重写逻辑
2. QA 增加基于工具或证据的事实核验
3. 落地 `qa.query` / `analyst.response` 局部追问闭环

### P2

完善可观测性与恢复能力：

1. 消息重试 / 死信 / ack 机制
2. 任务恢复与断点续跑
3. 更细粒度 Trace / agent_messages 持久化
4. 补足 service / web / agent 层自动化测试

## 8. 一句话记忆

CompeteAI 当前已经完成“5 Agent 工作流 MVP”，但真实执行仍是单进程串行编排；下一阶段的核心任务不是再加页面，而是把现有骨架升级为真正的消息驱动、多实例可运行的多智能体系统。
