## 2. 总目标

### MVP 定义

用户能在 Dashboard 提交一次竞品分析任务，后端执行真实分析流程，前端可查看：

1. 任务列表与状态（pending → running → completed / failed）
2. 结构化报告（SWOT、功能矩阵、定价、摘要）
3. 执行 Trace（至少 3～5 个阶段节点）

### MVP 不做

- Kafka 异步编排
- 完整 5 Agent 独立进程
- QA 打回闭环
- PDF 导出、Milvus RAG
- 复杂权限体系

## 4. 分阶段实施

### 阶段一：后端任务主链路（预计 2～3 天）

#### 4.1 数据模型（MVP 简化版）

第一版 **不拆 10 张细表**，用 JSON 列存报告与 Trace，降低联调成本。  
DTO 字段 **对齐前端** `frontend/src/types/index.ts`。

**表 `tasks`**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | VARCHAR(36) PK | UUID |
| user_id | BIGINT | 创建者（可选，MVP 可先 nullable） |
| title | VARCHAR(255) | 任务标题 |
| competitors | JSON | `string[]` |
| dimensions | JSON | `string[]`，如 `["功能","定价","SWOT"]` |
| status | VARCHAR(20) | pending / running / completed / failed / cancelled |
| progress | INT | 0–100 |
| agent_states | JSON | `AgentState[]` |
| error_message | TEXT | 失败原因 |
| created_at / updated_at | DATETIME | |

**表 `reports`**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 自增 |
| task_id | VARCHAR(36) UNIQUE | 一对一 |
| payload | JSON | 完整 `Report` 对象（见前端 types） |
| created_at | DATETIME | |

**表 `traces`**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 自增 |
| task_id | VARCHAR(36) UNIQUE | 一对一 |
| payload | JSON | 完整 `Trace` 对象 |
| created_at | DATETIME | |

**建议新增文件**

```
internal/repository/dao/task.go
internal/repository/dao/report.go
internal/repository/dao/trace.go
internal/repository/task.go      # Repository 接口
internal/repository/report.go
internal/repository/trace.go
internal/domain/task.go          # 领域类型（可选）
internal/service/task_service.go
internal/service/analysis_service.go   # 同步分析编排
internal/web/task.go
internal/web/report.go
internal/web/trace.go
scripts/mysql/migration_tasks.sql     # 可选，或 GORM AutoMigrate
```

在 `internal/repository/dao/init.go` 的 `InitTable` 中追加三张表的 AutoMigrate。

#### 4.2 API 契约（与前端对齐）

| 方法 | 路径 | 请求/响应 | 前端文件 |
|------|------|-----------|----------|
| POST | `/api/tasks` | Body: `CreateTaskPayload` → `Task` | `api/task.ts` |
| GET | `/api/tasks` | → `Task[]` | 同上 |
| GET | `/api/tasks/:id` | → `Task` | 同上 |
| DELETE | `/api/tasks/:id` | 204 | 同上 |
| POST | `/api/tasks/:id/clarify` | `{ answer }` | 同上（P1） |
| GET | `/api/tasks/:id/stream` | SSE 进度 | `composables/useTaskSSE.ts`（P1） |
| GET | `/api/reports/:taskId` | → `Report` | `api/report.ts` |
| GET | `/api/traces/:taskId` | → `Trace` | `api/trace.ts` |

**Wire 注册**：在 `wire.go` / `ioc/web.go` 注入 TaskHandler、ReportHandler、TraceHandler。

#### 4.3 同步分析服务（核心）

文件：`internal/service/analysis_service.go`

```
创建任务 (status=pending)
    ↓
异步 goroutine 或同步 HTTP（MVP 建议 goroutine + 立即返回 Task）
    ↓
status=running, progress=10, agent_states=[coordinator:running]
    ↓
① Collector 阶段：Firecrawl search + scrape（复用 ToolRegistry）
    ↓ 写 Trace 节点 collector
② Analyst 阶段：LLM 结构化提取 SWOT/功能/定价
    ↓ 写 Trace 节点 analyst
③ Writer 阶段：LLM 生成 summary + 报告 JSON
    ↓ 写 Trace 节点 writer
④ 可选 QA 阶段：LLM 打分 qaScore
    ↓ 写 Trace 节点 qa
写入 reports.payload
status=completed, progress=100
```

**可复用的现有能力**

- `internal/eino/chat_service.go` — LLM 调用模式
- `internal/eino/tool_registry.go` — Firecrawl 工具
- `internal/eino/tool_format.go` — 工具结果格式化

**Prompt 建议**

- 要求 LLM 输出 **严格 JSON**，字段对齐 `frontend/src/types/index.ts` 的 `Report`
- 解析失败时重试最多 3 次（与 plan.md 风险对策一致）
- 每条 SWOT / 功能结论尽量带 `sourceIds`，映射到 `sources` 字典

**MVP Trace 节点示例**（5 个即可演示）

```json
{
  "taskId": "xxx",
  "nodes": [
    { "id": "n1", "agent": "coordinator", "label": "任务拆解", "status": "completed", "durationMs": 120, "tokenCount": 800 },
    { "id": "n2", "agent": "collector", "label": "搜索与抓取", "status": "completed", "durationMs": 15000, "tokenCount": 0 },
    { "id": "n3", "agent": "analyst", "label": "结构化分析", "status": "completed", "durationMs": 8000, "tokenCount": 3200 },
    { "id": "n4", "agent": "writer", "label": "报告生成", "status": "completed", "durationMs": 6000, "tokenCount": 4100 },
```

**Step 1 — 环境**

**Step 3 — 异常态**

每页需覆盖：

- 空列表 / 报告未生成
- 加载中（`status=running`）
- 接口失败（toast + 重试）
- 任务失败（`errorMessage` 展示）

**Step 4 — SSE（P1）**

`useTaskSSE.ts` 已写好客户端，需在 Dashboard 创建任务后订阅 `/api/tasks/:id/stream`，实时更新 `progress` 与 `agentStates`。

## 6. 暂时不要优先做的事

| 事项 | 原因 |
|------|------|
| 立刻引入 Kafka | 增加运维与调试成本，MVP 用 goroutine 即可 |
| 拆 5 个独立 Agent 进程 | 先用「逻辑阶段 + Trace 节点」模拟角色 |
| 10 张细粒度 Schema 表 | JSON 列足够 MVP，细表留 P2 |
| UI 动效 / 精修 | 无真实数据前投入产出比低 |
| PDF 导出 | 报告 API 稳定后再做 |
| Chat 页继续扩展 | Chat 已可用，不阻塞 MVP |

## 7. 阶段验收标准

- [ ] `POST /api/tasks` 创建任务，返回 `status=running`

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| LLM 输出 JSON 不稳定 | JSON Mode + 校验 + 最多 3 次重试 |
| 分析耗时长导致 HTTP 超时 | 创建任务后立即返回；分析放 goroutine |
| 前后端 Report 字段不一致 | MVP 以 `frontend/src/types/index.ts` 为契约 |
| Firecrawl 限流/失败 | Trace 记录失败节点；task.status=failed |
| 演示时 LLM 不可用 | 保留 Mock 开关；准备一份静态 Report JSON 兜底 |
