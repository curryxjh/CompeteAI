# CompeteAI 企业级完善方案

> 更新时间：2026-06-09  
> 适用场景：2026-06-10 提交前的项目说明、答辩准备、后续工程演进

---

## 1. 文档目的

这份文档不讨论“再加几个页面”或“再堆几个 Agent 名称”，而是回答一个更关键的问题：

**CompeteAI 如何从一个已经可运行的多 Agent MVP，演进成更接近企业级、并更容易获得字节系评审认可的工程项目。**

核心原则只有三条：

1. **不虚报现状**：当前系统已经有多 Agent 骨架，但真实执行仍以单进程编排为主。
2. **先把闭环做实**：比起继续铺功能，更重要的是把任务、协作、回退、恢复、追踪做扎实。
3. **用工程质量拉开差距**：真正能和企业级项目竞争的，不是“概念多”，而是“稳定、可解释、可恢复、可扩展”。

---

## 2. 当前项目的真实定位

### 2.1 已有能力

当前代码已经具备以下核心能力：

- 任务创建、查询、删除、报告查询、Trace 查询、SSE 进度推送
- 5 个 Agent 的统一接口与注册机制
- Coordinator -> Collector -> Analyst -> Writer -> QA 的工作流
- QA 打回、用户澄清、任务取消、Trace 持久化
- 前端 Dashboard / Report / Trace / Agents / Chat 基础页面
- Tool 调用、来源溯源、结构化报告输出

相关代码入口：

- `internal/service/task_service.go`
- `internal/workflow/engine.go`
- `internal/workflow/dispatch.go`
- `internal/agent/`
- `internal/web/task.go`
- `internal/web/report.go`
- `internal/web/trace.go`
- `frontend/src/views/`

### 2.2 当前还不算“企业级多 Agent 系统”

当前系统更准确的定位是：

**单进程、多角色、可打回、可追踪的多 Agent 工作流 MVP**

而不是：

**真正消息驱动、跨实例部署、具备恢复和隔离能力的企业级多 Agent 平台**

关键原因：

1. Agent 执行仍主要由同一个 `Engine` 驱动
2. 事件中心 `TaskHub` 仍是进程内内存实现
3. Blackboard 虽然抽象了，但默认仍有单机内存路径
4. Kafka / Redis Stream 更像可选总线，而不是默认事实标准
5. 任务恢复、重试、幂等、死信、断点续跑能力还不完整
6. 自动化测试、构建稳定性、部署可观测性仍不足

### 2.3 这并不是坏事

这不是项目失败，而是项目正处于一个非常典型、也是非常合理的阶段：

**架构方向是对的，MVP 已经成立，下一步该从“能跑”升级到“能稳、能解释、能扩”。**

## 3. 明天提交时应该怎么定义这个项目

如果在 **2026-06-10** 提交，最合适的表述不是“我们已经做成企业级分布式多 Agent 平台”，而是：

> CompeteAI 已完成多 Agent 协作 MVP，具备任务编排、信息采集、结构化分析、报告生成、QA 打回、用户澄清、Trace 追踪等完整闭环；当前版本采用单进程工作流编排实现快速验证，已为消息驱动、跨实例部署和共享状态演进预留明确架构边界。

这个表述有三个好处：

1. **诚实**：不夸大当前实现
2. **专业**：说明你知道系统下一步该如何演进
3. **有工程判断**：表现出你不是只会堆功能，而是懂架构阶段性取舍

### 3.1 提交时要重点强调的点

- 不是简单 Chat，而是**任务型 Agent 工作流**
- 不是纯页面展示，而是**后端真实任务闭环**
- 不是黑盒输出，而是**有 Trace、有来源、有打回**
- 不是单次生成，而是**具备自校验与重做机制**

### 3.2 提交时不要过度承诺的点

- 不要说“已经是分布式多 Agent 平台”
- 不要说“Kafka 已完整驱动所有 Agent”
- 不要说“支持企业级生产部署”
- 不要说“高可用、可扩容、强一致能力已经完善”

评审通常不怕你阶段性没做完，怕的是你**对系统现状判断失真**。

## 4. 字节系评审更容易认可的项目特征

如果要让这个项目更接近字节会认可的工程作品，重点不是“概念更花”，而是下面五件事。

### 4.1 明确的系统边界

一个成熟项目必须回答清楚：

- 用户请求如何进入系统
- Agent 如何被调度
- 状态写到哪里
- 失败后如何恢复
- 结果如何被审计和回放

CompeteAI 已经有这套骨架，但需要把它从“代码层面存在”升级到“运行层面可靠”。

### 4.2 真实的 Agent 协作，而不是函数串行调用

企业级评审更看重的是：

- Agent 是否真的有独立职责
- 是否能基于消息协作
- 是否支持局部返工
- 是否能通过共享上下文继续工作

当前项目已经有 `qa.query -> analyst.response` 的雏形，这条路线值得继续深化。

### 4.3 强可观测性

真正好的项目必须能回答：

- 这个任务现在卡在哪个 Agent
- 哪个环节耗时最长
- 哪个结论引用了哪些来源
- 为什么 QA 打回
- 为什么这次结果比上次更好或更差

Trace、Token、来源面板、回放能力，都是很有价值的差异化亮点。

### 4.4 失败可恢复

企业项目和 Demo 项目最大的差别之一就是：

**失败时是否还能继续。**

需要逐步具备：

- 消息幂等
- Worker 重试
- 任务断点恢复
- 死信记录
- 手工重放

### 4.5 工程质量而不是功能堆叠

真正能拉开差距的，是这些能力：

- 构建稳定
- 配置清晰
- 测试可跑
- 日志可查
- 错误有分类
- 安全边界清楚

## 5. 目标架构：从 MVP 到企业级

建议将后续架构目标定义为以下五层：

### 5.1 接入层

- Web API
- SSE / WebSocket 推送
- 鉴权、限流、审计

### 5.2 编排层

- 任务入口
- Workflow Router
- Rework / Clarification 状态机
- 任务恢复控制器

### 5.3 Agent Worker 层

- Coordinator Worker
- Collector Worker
- Analyst Worker
- Writer Worker
- QA Worker

每个 Worker 只做一件事：

- 消费自己的输入消息
- 读取共享状态
- 执行本角色逻辑
- 产出消息与工件

### 5.4 共享状态与消息层

- Redis Blackboard
- Kafka 或 Redis Stream Bus
- 幂等键
- 任务 Checkpoint
- 事件审计流

### 5.5 存储与观测层

- MySQL 持久化任务、报告、Trace、事件
- 日志系统
- Metrics
- Token / 成本统计
- 任务回放与调试工具

## 6. 推荐演进路线

下面这条路线兼顾现实性和工程含金量。

### 阶段 A：提交前必须补齐

目标：让项目在提交时呈现为“完成度高、表达准确、演示可靠”。

必须完成：

1. 修复前端构建问题，确保 `frontend` 可稳定打包
2. 至少跑通一次完整链路：
   - 创建任务
   - Agent 执行
   - QA 通过或打回
   - 报告生成
   - Trace 可查看
3. 准备 1 个稳定 Demo Case
4. 整理文档，统一项目现状描述
5. 在答辩里明确说明当前是“单进程编排 MVP + 可演进多 Agent 架构”

提交前最重要的不是“再写一个功能”，而是：

**让评审看到你做成了什么，以及你清楚下一步该怎么做。**

### 阶段 B：提交后 3 天内

目标：把“能跑”变成“稳跑”。

优先级：

1. 补 workflow / repository / web 层基础测试
2. 修复阻塞性构建和运行问题
3. 明确错误码、错误类型、重试策略
4. 补任务失败后的错误展示和手工重试入口

### 阶段 C：提交后 1 周内

目标：完成从单进程工作流到消息驱动协作的第一步。

优先级：

1. Redis Blackboard 默认启用
2. TaskHub 事件持久化或迁移到可跨实例消费的流式通道
3. 将 QA 和 Analyst 先拆成两个独立 Worker
4. 跑通 `qa.query -> analyst.response -> qa.recheck`

为什么先拆这两个：

- 它们最能体现“Agent 协作”
- 最容易向评审展示“局部追问、局部修正”
- 比全部 Agent 一次性拆分风险更低

### 阶段 D：提交后 2 周内

目标：形成真正的多 Worker 执行模型。

优先级：

1. Coordinator / Collector / Writer / QA / Analyst 全部独立消费
2. Engine 只保留入口、路由、恢复控制
3. 引入消息幂等、重试、超时、死信
4. 完善任务断点恢复和重放机制

### 阶段 E：提交后 1 个月内

目标：向企业级平台靠拢。

优先级：

1. 细粒度 Trace、事件审计、运行指标
2. Token / 成本治理
3. 多租户与权限边界
4. 插件化 Tool Registry
5. 回归测试、压测、部署脚本、CI/CD

## 7. 需要重点补强的企业级能力

### 7.1 稳定性

建议增加：

- 统一超时控制
- 指数退避重试
- 熔断与降级
- 工具调用失败回退策略

### 7.2 一致性与恢复

建议增加：

- 消息幂等键
- Task Checkpoint
- Trace 追加式写入
- Worker Crash 后恢复执行

### 7.3 可观测性

建议增加：

- 每个 Agent 的耗时、Token、重试次数
- 每个任务的关键状态迁移日志
- QA 打回原因分布
- 来源引用覆盖率

### 7.4 质量保障

建议增加：

- 单元测试
- 集成测试
- Demo 回放用例
- Prompt 输出结构校验

### 7.5 安全与治理

建议增加：

- 鉴权边界统一化
- 审计日志
- API 限流
- 敏感配置隔离
- 输入校验与输出脱敏

## 8. 最能体现项目竞争力的三项改进

如果时间有限，只做最值钱的三件事，我建议是：

### 8.1 把 QA 打回做成“局部返工”而不是“整链重跑”

这会显著提高项目成熟度。

理想效果：

- QA 发现摘要无证据
- 向 Analyst 追问具体 claim
- Analyst 补来源与解释
- Writer 只重写对应段落
- QA 复检通过

这比“从头再跑一次”更像真实企业 Agent 协作。

### 8.2 把事件与状态迁出进程内存

这一步是从 Demo 到工程系统的分水岭。

需要迁出的最小集合：

- SSE 事件
- clarification
- cancel
- workflow checkpoint

### 8.3 把 Trace 做成一等公民

一个能让评审记住的系统，不只是结果好，还要：

- 看得见过程
- 查得到来源
- 说得清责任

建议把 Trace 定义为项目核心资产，而不是附属日志。

## 9. 提交答辩时建议这样讲

建议按这个顺序介绍项目：

1. **业务问题**
   - 竞品分析不是一次文本生成，而是多角色协同、证据驱动、可回溯的复杂任务

2. **系统方案**
   - 用 5 个 Agent 模拟真实调研团队
   - 用任务流、共享上下文、QA 打回和 Trace 实现闭环

3. **当前成果**
   - 已实现任务创建、采集、分析、写作、质检、打回、澄清、报告、Trace

4. **工程判断**
   - 当前版本采用单进程编排快速验证 MVP
   - 已预留消息驱动与共享状态边界

5. **下一步演进**
   - 独立 Worker、Redis Blackboard、消息幂等、断点恢复、局部返工

这样讲会让评审看到两点：

- 你已经做出了真实东西
- 你知道怎么把它继续做成更强的系统

---

## 10. 结论

CompeteAI 当前最值得肯定的地方，不是“已经完全企业级”，而是：

- 已经完成了一个真实可运行的多 Agent 任务闭环
- 已经具备了进一步工程化的正确架构边界
- 已经有条件从 MVP 演进到真正消息驱动、可恢复、可观测的协作系统

如果目标是“与企业级项目竞争、争取被字节认可”，正确路线不是继续堆概念，而是沿着下面这条主线持续完善：

**闭环真实化 -> 协作消息化 -> 状态共享化 -> 恢复机制化 -> 观测体系化**

只要把这条路线讲清楚、做扎实，这个项目就不再只是一个比赛 Demo，而会更像一个有明确产品价值和工程深度的智能协作系统。
