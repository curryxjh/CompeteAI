# 长期记忆系统设计

更新时间：2026-06-09

## 1. 文档目标

本文档给出 CompeteAI 长期记忆系统（Long-term Memory）的第一版工程设计，目标是将当前项目从“任务级共享状态”升级为“任务状态 + 长期知识 + 显式偏好 + 任务经验”的多层记忆架构。

本文档覆盖：

- 现状判断与设计边界
- 记忆系统分层
- 模块职责与目录规划
- Go 接口设计
- MySQL 元数据表结构
- PostgreSQL / pgvector 向量表结构
- 写入时机
- 检索与注入点
- 排序、去重、失效与治理策略
- 可观测性与实施计划

本文档默认遵循当前项目既有架构与目录设计，重点兼容以下现有实现：

- `internal/state/blackboard.go`
- `internal/state/task_board.go`

- `internal/agent/coordinator.go`
- `internal/agent/collector.go`

## 2. 现状与问题

## 2.1 当前“记忆”真实形态

当前项目已经具备一套运行中的共享状态机制，但它本质上是 **Execution Memory**，不是长期记忆系统。

当前主要特征：

1. 通过 `Blackboard` 抽象统一读写任务上下文。
2. Key 以 `task:{taskID}:{scope}:{field}` 组织。
3. 数据主要覆盖：
   - `task.*`
   - `workflow.*`
   - `collector.*`
   - `analysis.*`
   - `report.*`
   - `qa.*`
4. Redis Blackboard 具备 TTL，适合短期任务态，不适合长期知识沉淀。
5. 当前缺少用户级、项目级、实体级、组织级长期记忆作用域。
6. 当前没有 embedding、向量检索、实体归一、事实去重、失效治理等长期记忆核心能力。

结论：

**当前系统有任务级记忆，没有长期知识记忆。**

---

## 2.2 当前实现已经解决的问题

当前 blackboard 已经很好地解决了以下问题：

- 多 Agent 共享任务上下文
- 工作流状态与轮次管理
- 中间产物复用
- QA 打回后的重跑
- 澄清问题闭环
- Trace 与事件审计

这部分设计不应推翻，而应保留为长期记忆系统的底层运行态支撑。

---

## 2.3 当前缺失的问题

当前系统尚未解决：

1. 历史任务知识无法跨任务复用
2. 用户偏好与项目规范无法稳定注入
3. 竞品实体无法做长期事实沉淀
4. 证据与结论之间缺少结构化关联
5. QA 结果无法反哺长期事实质量
6. 历史报告只能作为文本存档，不能作为可检索知识

---

## 3. 设计原则

长期记忆系统遵循以下原则：

### 3.1 不替代 Blackboard

长期记忆系统不替代现有 `Blackboard`。  
`Blackboard` 继续负责单次任务的执行态共享。

### 3.2 结构化优先

长期记忆优先存储“事实、偏好、经验、证据”，而不是整段自由文本。

### 3.3 证据优先

所有可长期复用的事实都必须尽量绑定来源和证据。

### 3.4 分层装配

Agent 运行时上下文不应直接拼接所有历史数据，而应按层装配：

- 执行态
- 显式偏好
- 长期事实
- 历史经验
- 证据片段

### 3.5 可治理

长期记忆不是只进不出。  
必须支持：

- 去重
- 合并
- 降权
- 过期
- 失效
- 人工修正

### 3.6 面向现有工程渐进演进

第一版设计必须能在当前 Go + MySQL + Redis + Eino 架构中逐步落地，不要求一次性重构整套工作流。

## 4. 总体架构

## 4.1 四层记忆架构

建议将系统记忆分成四层：

### L0: Execution Memory

任务执行态记忆，继续由现有 Blackboard 承担。

职责：

- 保存当前任务输入、产物、状态
- 支撑 Agent 间共享上下文
- 支撑打回、澄清、恢复

特点：

- 任务级
- 短期
- 强一致性要求高
- 不承担长期知识沉淀

---

### L1: Explicit Memory

显式记忆，类似 Claude Code 的 `CLAUDE.md`。

职责：

- 保存用户、项目、组织的显式规则和偏好
- 提供稳定、可编辑、可审查的高优先级上下文

示例：

- 默认竞品维度
- 报告语气与结构规范
- 可信源白名单
- 禁止使用的表述
- QA 最低门槛
- 中文术语规范

---

### L2: Fact Memory

长期事实记忆，类似 mem0 的长期记忆核心。

职责：

- 保存跨任务可复用的结构化事实
- 绑定实体、作用域、证据、时间和可信度
- 提供检索与二次注入能力

示例：

- 某竞品的定价套餐
- 某竞品的核心功能
- 某品牌的目标人群
- 已验证的 SWOT 要点

---

### L3: Episode Memory

任务经验记忆。

职责：

- 保存一次任务的复盘摘要、失败原因、打回教训、澄清结果
- 帮助未来类似任务快速复用经验

示例：

- 某类任务常见问题
- 某类竞品分析时容易缺失的维度
- 某项目的高分报告结构

---

## 4.2 存储选型

由于 `pgvector` 不能运行在 MySQL 中，推荐采用双存储方案：

### MySQL

负责：

- scope
- entity
- fact
- source
- evidence link
- claim
- episode
- preference
- memory event

特点：

- 适合业务元数据、约束和审计
- 便于与当前 GORM 体系兼容

### PostgreSQL + pgvector

负责：

- fact embedding
- evidence chunk embedding
- episode embedding
- preference embedding（按需）

特点：

- 专注向量检索
- 可重建
- 与业务主数据解耦

## 5. 作用域模型

## 5.1 作用域类型

长期记忆至少支持以下 scope：

| ScopeType | 说明 | 示例 |
|---|---|---|
| `user` | 用户级偏好和个人历史 | `user:1001` |
| `workspace` | 团队或组织级规范 | `workspace:acme` |
| `project` | 项目级规则和沉淀 | `project:compete-ai` |
| `entity` | 实体级知识 | `entity:notion` |
| `global` | 全局默认知识 | `global:default` |

---

## 5.2 作用域优先级

运行时加载优先级：

```text
runtime override
> project explicit memory
> user explicit memory
> workspace explicit memory
> project fact memory
> entity fact memory
> workspace fact memory
> global memory
```

说明：

- 偏好类信息优先级高于历史事实。
- 项目显式规则优先于用户偏好。
- 事实类信息按与当前任务相关性排序，而不是仅按层级硬覆盖。

## 6. 数据模型

## 6.1 Scope

Scope 表示记忆的归属与应用边界。

关键字段：

- `scope_type`
- `scope_key`
- `display_name`
- `owner_user_id`
- `owner_org_id`
- `project_id`

---

## 6.2 Entity

Entity 表示长期知识锚点。

候选实体类型：

- `competitor`
- `brand`
- `product`
- `feature`
- `pricing_plan`
- `persona_segment`
- `market_term`

Entity 必须支持：

- 别名
- 归一化名称
- 外部引用
- 首次出现和最近出现时间

---

## 6.3 Fact

Fact 是长期记忆的核心对象。

建议采用三元结构：

```text
subject + predicate + object
```

示例：

```text
Notion + has_pricing_plan + {"name":"Plus","price":"$10/user/month"}
```

Fact 必须携带：

- `fact_type`
- `subject`
- `predicate`
- `object_value_json`
- `object_text`
- `summary`
- `confidence_score`
- `freshness_score`
- `importance_score`
- `verification_status`
- `status`
- `source_count`
- `first_seen_at`
- `last_seen_at`

---

## 6.4 Evidence

Evidence 不是独立“事实”，而是事实的支撑材料。

Evidence 至少包含：

- 来源 URL
- 来源域名
- 标题
- 摘要或原始片段
- 原始 chunk
- 引文区间
- 支撑类型
- 支撑强度

---

## 6.5 Claim

Claim 用于区分“模型结论”和“已验证事实”。

原因：

- Analyst/Writer 的输出不应直接视作永久事实
- 未经 QA 或证据绑定的结论只能先当 claim 存档

Claim 常见状态：

- `pending`
- `verified`
- `rejected`
- `invalid`

---

## 6.6 Episode

Episode 表示一次任务经验。

Episode 保存：

- 任务 query
- competitor 列表
- dimension 列表
- 任务摘要
- QA 分数
- 结果状态
- 经验教训
- 关键 artifact 索引

---

## 6.7 Preference

Preference 表示显式偏好。

示例 key：

- `report.style`
- `report.section_order`
- `source.trusted_domains`
- `analysis.default_dimensions`
- `qa.min_score`
- `terminology.zh_cn`

## 8. Go 接口设计

## 8.1 对外服务接口

```go
package memory

import "context"

type MemoryService interface {
    BuildAgentContext(ctx context.Context, req BuildContextRequest) (AgentMemoryContext, error)

    IngestCollectorOutput(ctx context.Context, req IngestCollectorRequest) error
    IngestAnalysisOutput(ctx context.Context, req IngestAnalysisRequest) error
    IngestQAResult(ctx context.Context, req IngestQARequest) error
    IngestTaskCompletion(ctx context.Context, req IngestEpisodeRequest) error

    UpsertPreference(ctx context.Context, req UpsertPreferenceRequest) error
    SearchFacts(ctx context.Context, req SearchFactsRequest) ([]Fact, error)
    SearchEvidence(ctx context.Context, req SearchEvidenceRequest) ([]EvidenceChunk, error)

    ResolveEntities(ctx context.Context, req ResolveEntitiesRequest) ([]Entity, error)
    InvalidateFact(ctx context.Context, factID string, reason string) error
}
```

## 8.4 Agent RunInput 扩展建议

当前 `agent.RunInput` 中没有长期记忆注入位。  
建议新增：

```go
type RunInput struct {
    TaskID       string
    TraceID      string
    Attempt      int
    TriggerType  string
    Reason       string
    Payload      map[string]any

    Memory AgentMemoryContext
}
```

这样可由工作流层统一装配长期记忆，而不是每个 Agent 单独访问 MemoryService。

## 10. PostgreSQL / pgvector 表结构设计

## 10.1 memory_embeddings

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE memory_embeddings (
  id            UUID PRIMARY KEY,
  object_type   VARCHAR(32) NOT NULL,
  object_id     UUID NOT NULL,
  scope_type    VARCHAR(32) NOT NULL,
  scope_key     VARCHAR(128) NOT NULL,
  entity_id     UUID NULL,
  content_text  TEXT NOT NULL,
  metadata_json JSONB NOT NULL DEFAULT '{}'::jsonb,
  embedding     vector(1536) NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_mem_embed_object ON memory_embeddings (object_type, object_id);
CREATE INDEX idx_mem_embed_scope  ON memory_embeddings (scope_type, scope_key);
CREATE INDEX idx_mem_embed_entity ON memory_embeddings (entity_id);

CREATE INDEX idx_mem_embed_vec
ON memory_embeddings
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

说明：

- 仅承担向量检索职能
- 业务真相仍以 MySQL 为主
- embedding 可重建

## 10.2 memory_chunks

```sql
CREATE TABLE memory_chunks (
  id            UUID PRIMARY KEY,
  source_id     UUID NOT NULL,
  task_id       VARCHAR(64) NOT NULL,
  chunk_index   INT NOT NULL,
  content_text  TEXT NOT NULL,
  token_count   INT NOT NULL,
  metadata_json JSONB NOT NULL DEFAULT '{}'::jsonb,
  embedding     vector(1536) NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()

CREATE INDEX idx_chunk_source ON memory_chunks (source_id, chunk_index);
CREATE INDEX idx_chunk_task   ON memory_chunks (task_id);

CREATE INDEX idx_chunk_vec
ON memory_chunks
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

说明：

- 对原始来源进行 chunk 化与向量化
- 供 Analyst 和 QA 做证据检索

## 11. 运行时上下文装配

## 11.1 AgentMemoryContext 分层

运行时长期记忆上下文建议分层装配：

### L1 Explicit

- 项目级显式规则
- 用户级偏好
- 组织级约束

### L2 Facts

- 与当前 competitors / dimensions 相关的已验证事实
- 高重要度、较新鲜的长期事实

### L3 Episodes

- 相似历史任务摘要
- 高分任务的 lessons learned

### L4 Evidence

- 与当前 query 最相关的来源 chunk
- Analyst / QA 使用最多

---

## 11.2 组装入口

建议在工作流层统一组装，而不是各 Agent 自行检索。

推荐注入点：

- `internal/workflow/dispatch.go`
- `buildRunInput(...)`

流程：

1. 从 blackboard 读取当前任务元信息
2. 构造 `BuildContextRequest`
3. 调用 `MemoryService.BuildAgentContext(...)`
4. 将结果写入 `agent.RunInput.Memory`

优点：

- 记忆注入统一治理
- Agent 逻辑更干净
- 便于统一打点和调优

---

## 11.3 Token 预算建议

不同 Agent 的记忆预算应不同：

| Agent | 建议长期记忆预算 |
|---|---:|
| Coordinator | 400 tokens |
| Collector | 500 tokens |
| Analyst | 1800 tokens |
| Writer | 1200 tokens |
| QA | 1500 tokens |

原则：

- Coordinator 主要吃偏好和历史任务经验
- Analyst/QA 主要吃事实和证据
- Writer 主要吃显式写作规则和高分历史案例摘要

## 12. 检索设计

## 12.1 检索维度

长期记忆检索不能只靠向量相似度，至少要结合：

1. 语义相关性
2. scope 匹配度
3. entity 命中度
4. freshness
5. confidence
6. source reliability

---

## 12.2 排序公式

建议第一版采用加权排序：

```text
final_score =
0.40 * semantic_score +
0.20 * scope_score +
0.15 * entity_match_score +
0.10 * freshness_score +
0.10 * confidence_score +
0.05 * source_reliability_score
```

补充规则：

- `verified` fact 对 `pending` fact 加权提升
- `invalid` fact 不参与候选
- 同一 predicate 最多保留 3 条
- 同一来源域名的证据最多保留 2 个 chunk

---

## 12.3 Retrieval Trace

建议保留调试信息：

- 原始 query
- 重写后的 query
- 召回候选数
- 过滤原因
- 最终注入对象列表
- token 占用

这部分可写入 `AgentMemoryContext.Debug`，便于前端回放和离线调参。

## 17. 事实写入策略

## 17.1 允许入库的事实类型

允许入长期事实库的类型：

1. `extracted`
   - 直接从来源提取的事实
2. `normalized`
   - 结构清洗后的提取事实
3. `verified_inference`
   - 经 QA 或证据交叉验证的推断事实

---

## 17.2 不允许入库的内容

以下内容不得写入长期事实：

- 无来源 URL
- 来源不可追溯
- 纯模型常识补全
- 时效性极强但没有时间戳
- 仅出现在报告总结中、无证据绑定的结论

---

## 17.3 去重策略

去重键建议为：

```text
scope_id + normalized(subject,predicate,object) -> sha256
```

去重后的合并策略：

- 更新 `last_seen_at`
- 累加 `source_count`
- 使用更高可靠来源提升 `confidence_score`
- 若新证据冲突，则标记 `pending_review`

---

## 18. 治理策略

## 18.1 状态机

Fact 状态建议：

- `active`
- `stale`
- `invalid`
- `archived`

Verification 状态建议：

- `pending`
- `verified`
- `rejected`
- `needs_review`

---

## 18.2 衰减策略

建议配置：

- `decay_after_days = 90`
- `stale_after_days = 180`
- `invalid_after_days = 365`

逻辑：

- 长时间未见新证据的事实降低 freshness
- 严重过期的事实进入 stale
- 被 QA 明确否定或长期冲突的事实进入 invalid

---

## 18.3 QA 反哺

QA 对长期记忆的影响必须显式记录：

- 通过：提升 confidence
- 无支撑：降权
- 来源缺失：不予验证
- 明显错误：invalid

---

## 18.4 人工治理

后续可补充后台能力：

- 手工失效事实
- 手工提升可信度
- 手工维护别名映射
- 手工编辑显式偏好

## 23. 风险与边界

## 23.1 风险

1. 事实抽取质量不足，导致长期记忆脏化
2. 向量检索结果过宽，导致上下文污染
3. 事实与 claim 未分层，导致幻觉沉淀
4. 记忆注入过多，导致 prompt 膨胀

---

## 23.2 控制策略

1. 先少量注入，再逐步扩张
2. 先建立 claim/fact 分层，再开放自动升格
3. 先以 verified facts 为主，pending facts 为辅
4. 保留 Retrieval Trace，支持离线调参

---

## 24. 最终结论

CompeteAI 当前已经具备成熟的任务级共享状态机制，但还缺少长期记忆层。

最合理的演进方式不是重写 Blackboard，而是在其上方新增一套分层长期记忆系统：

1. `Execution Memory`
   - 继续由 Blackboard 承担
2. `Explicit Memory`
   - 项目/用户显式规则
3. `Fact Memory`
   - 可验证、可检索、可治理的长期事实
4. `Episode Memory`
   - 跨任务经验沉淀

第一版落地建议采用：

- MySQL：主业务元数据和事实
- PostgreSQL + pgvector：向量检索
- 工作流层统一注入
- Collector / Analyst / QA / completeTask 分阶段写入

这样可以在不破坏现有工作流主链路的前提下，把系统从“任务驱动协作”升级到“任务驱动 + 长期知识复用”的更高形态。
