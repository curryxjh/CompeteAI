# CompeteAI 项目结构详解

## 一、项目概述

**CompeteAI** 是一个 Go 语言实现的多 Agent 协作竞品分析系统。最终目标是构建 5 个专职 Agent（Coordinator → Collector → Analyst → Writer → QA），通过 Kafka + Shared State 双层通信、Eino Graph 编排、反馈闭环机制，自动完成从公开信息采集到结构化竞品报告的全链路产出。

**当前阶段**：项目处于基础设施搭建阶段，已完成用户认证模块（注册、登录、JWT 双 Token、Session 管理）和分层架构骨架，前端 Vue 3 项目已脚手架就绪。

**核心信息**：

| 项目 | 值 |
|---|---|
| Go 版本 | 1.26.2 |
| 模块名 | `CompeteAI` |
| HTTP 框架 | Gin |
| ORM | GORM + MySQL 8.0 |
| 缓存 | Redis 5.0.7 |
| 配置 | Viper（支持热加载） |
| 日志 | Zap + Lumberjack（日志轮转） |
| 依赖注入 | Google Wire |
| JWT | golang-jwt/jwt v5 |
| 前端 | Vue 3.5 + TypeScript + Vite 6 + Element Plus + ECharts |
| 默认端口 | 后端 8084 / 前端 5173 / MySQL 3308 / Redis 26379 |

## 四、ioc/ — 依赖注入（Inversion of Control）

### ioc/db.go

**`InitDB()`**：创建 GORM MySQL 连接，配置连接池（最大 200 / 空闲 50），自动迁移表结构（`dao.InitTable`）。失败直接 panic。

### ioc/redis.go

**`InitRedis()`**：创建 `redis.Client`，返回 `redis.Cmdable` 接口。
**`NewRateLimiter()`**：创建 Redis 滑动窗口限流器。

### ioc/web.go

**`InitWebServer(mdls, userHdl)`**：创建 Gin Engine，应用中间件，注册用户路由。

**`InitMiddlewares(redisClient, jwtHdl)`**：返回 3 个中间件：

| 顺序 | 中间件 | 说明 |
|---|---|---|
| 1 | CORS | 允许 localhost + HTTPS，暴露 `x-jwt-token` / `x-refresh-token` 头 |
| 2 | 限流 | Redis 滑动窗口，每 IP 100 次/秒 |
| 3 | JWT 鉴权 | 跳过 `/users/login`、`/users/signup`、`/users/refresh_token` |

## 六、internal/repository/ — 数据访问层

采用 **Repository 模式**，分为三层：Repository（门面）→ DAO（数据库操作）→ Cache（缓存）。

### 六.1 internal/repository/user.go — Repository 层

`UserRepository` 接口提供 `Create`、`FindByUserName`、`FindByEmail`、`FindById`。

`CachedUserRepository` 组合 DAO + Cache，核心策略：

| 操作 | 缓存策略 |
|---|---|
| `Create` | 直接走 DB，不写缓存 |
| `FindByUserName` | 直接走 DB，不查缓存 |
| `FindByEmail` | 直接走 DB，不查缓存 |
| `FindById` | **Cache-Aside**：先查 Redis → 未命中则查 DB → 异步回填缓存（TTL 5 分钟） |

**Entity-Domain 映射**：`entityToDomain()` / `domainToEntity()` 在 DAO 的 GORM 实体和领域模型之间转换，确保领域层不依赖 GORM。

### 六.2 internal/repository/dao/ — DAO 层

#### dao/user.go

`GORMUserDao` 实现 `UserDao` 接口：

- GORM 实体字段：`Id`（主键自增）、`Email`（唯一索引，`sql.NullString`）、`UserName`、`Password`、`Utime`/`Ctime`（Unix 毫秒）
- `Insert`：捕获 MySQL 1062 错误（唯一键冲突）转为 `ErrUserDuplicate`
- 所有查询使用 `WithContext(ctx)` 传递上下文

#### dao/init.go

`InitTable(db)`：调用 GORM `AutoMigrate(&User{})` 自动建表。

### 六.3 internal/repository/cache/ — 缓存层

#### cache/user.go

`RedisUserCache` 实现 `UserCache` 接口：

- Key 格式：`user:info:<id>`
- TTL：5 分钟
- 序列化：JSON（`domain.User` ↔ `[]byte`）
- 未命中：返回 `redis.Nil`，上层做异步回填

### internal/service/user.go

`userService` 实现 `UserService` 接口：

|---|---|

## 八、internal/web/ — HTTP 层

### 八.1 web/user.go — 用户接口

路由注册（前缀 `/users`）：

| 方法 | 路径 | 处理器 | 鉴权 |
|---|---|---|---|
| POST | `/users/signup` | `SignUp` | 无需 |
| POST | `/users/login` | `LogInJWT` | 无需 |
| POST | `/users/logout` | `LogoutJWT` | 需要 |
| POST | `/users/refresh_token` | `RefreshToekn` | 无需（用 Refresh Token） |

**SignUp 校验规则**：邮箱格式 → 两次密码一致 → 密码复杂度（8 位以上，含字母+数字+特殊字符），使用 `regexp2` 库。

### 八.2 web/jwt/ — JWT 认证

#### jwt/types.go

两种 Token：

| Token | 过期 | Claims |
|---|---|---|
| Access Token | 30 分钟 | `Uid`、`UserAgent`（防劫持）、`Ssid`（Session ID） |
| Refresh Token | 7 天 | `Uid`、`Ssid` |

#### jwt/redis_jwt.go

`RedisJwtHandler` 实现完整 Token 管理：

```
登录流程：
1. 验证用户名密码
2. 生成 UUID 作为 Ssid
3. 签发 Access Token + Refresh Token
4. 写入响应头 x-jwt-token / x-refresh-token

登出流程：
1. 提取 Access Token 中的 Ssid
2. Redis 写入 users:ssid:<uuid>（TTL 7天，黑名单机制）
3. 清除响应头 Token

刷新流程：
1. 从 Authorization 头提取 Refresh Token
2. 解析并验证
3. 检查 Ssid 是否在黑名单（Redis 查 users:ssid:<uuid>）
4. 签发新的 Access Token + Refresh Token 对
```

### 八.3 web/middleware/ — 中间件

#### middleware/login_jwt.go

JWT 鉴权中间件（Builder 模式）：

```
请求 → 跳过白名单路径？
     → 提取 Authorization: Bearer <token>
     → 解析 JWT，验证签名和过期
     → 验证 UserAgent 一致性（防 Token 劫持）
     → 检查 Ssid 是否在黑名单（Redis）
     → 将 UserClaims 注入 Gin Context
     → 放行 / 返回 401
```

## 九、internal/pkg/ — 公共工具包

### 九.1 pkg/logger/ — 日志系统（8 个文件）

基于 **Zap** 的完整日志抽象：

```
Logger 接口 (types.go)
    ├── ZapLogger (zap_logger.go)       → 包装 *zap.Logger
    ├── NopLogger (nop.go)              → 空操作，默认全局 Logger
    └── Manager (manager.go)            → Tee Core：同时输出到文件 + 控制台
         ├── Lumberjack                 → 文件日志轮转
         └── Console Encoder            → 控制台彩色输出

全局 Logger (global_instance.go)：
    SetGlobalLogger() / L()             → 读写锁保护的线程安全单例

Gin 集成 (gin_logger.go)：
    GinLogger()                         → 请求日志中间件
    GinRecovery()                       → Panic 恢复中间件
```

**日志字段构造函数**（`fields.go`）：`String`、`Int`、`Int64`、`Duration`、`Bool`、`Error`、`Any`。

### 九.2 pkg/ratelimit/ — 限流

**Redis 滑动窗口限流**：

```
slide_window.lua（原子执行）：
1. ZREMRANGEBYSCORE  删除窗口外的过期记录
2. ZCOUNT            统计窗口内请求数
3. 超过阈值 → 返回限流
4. 未超过   → ZADD 当前时间戳 + PEXPIRE 设置过期
```

### 九.3 pkg/ginx/ — Gin 工具

- `result.go`：标准 JSON 响应结构 `{ Code, Msg, Data }`
- `middleware/ratelimit/builder.go`：Gin 限流中间件，按 IP 限流，返回 429

## 十三、架构模式总结

项目中使用的设计模式：

| 模式 | 位置 | 说明 |
|---|---|---|
| **分层架构** | web → service → repository → dao/cache | 严格单向依赖，上层不感知下层实现 |
| **Repository 模式** | `internal/repository/` | 接口抽象数据访问，Entity-Domain 映射隔离 GORM |
| **依赖注入** | `wire.go` / `wire_gen.go` | Google Wire 编译期 DI，零运行时开销 |
| **Cache-Aside** | `repository/user.go` | 先查缓存，未命中查 DB，异步回填 |
| **Builder 模式** | `middleware/login_jwt.go` / `ratelimit/builder.go` | 流式 API 配置中间件 |
| **接口隔离** | 所有层 | DAO、Cache、Repository、Service、Handler 均为接口，便于测试 |
| **双 Token JWT** | `web/jwt/` | 短 Access Token + 长 Refresh Token |
| **Session 黑名单** | `web/jwt/redis_jwt.go` | Redis 记录已登出 Ssid，实现主动失效 |
| **滑动窗口限流** | `pkg/ratelimit/` | Redis Sorted Set + Lua 原子脚本 |
| **Tee Logger** | `pkg/logger/manager.go` | 同时输出文件 + 控制台 |
