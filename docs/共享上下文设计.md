# 共享上下文设计

## 1. 文档目标

本文档定义多 Agent 工作流中的共享上下文（Blackboard）设计，用于统一管理任务状态、阶段产物、来源信息、分析结果、报告草稿和 QA 结果。

Blackboard 的目的不是替代数据库，而是为 Agent 协作提供一块稳定的“共享工作台”。

---

## 2. 落位目录

建议新增目录：

```text
internal/
├── state/
│   ├── blackboard.go
│   ├── keys.go
│   └── redis.go
```

建议职责分配：

- `blackboard.go`
  - 接口定义
- `keys.go`
  - Key 规范
- `redis.go`
  - Redis 实现

如果先不接 Redis，可以先做内存实现，但接口名称和字段命名不要改。

---

## 3. 设计原则

### 3.1 Agent 通过 Blackboard 协作

Agent 不直接调用其他 Agent 的方法来拿数据，而是从 Blackboard 读取上游产物。

### 3.2 结构分区清晰

共享上下文按职责分区，避免一个大 JSON 混装所有字段。

### 3.3 写入责任明确

每个字段必须有唯一的主要写入者，避免多个 Agent 同时覆盖。

### 3.4 留痕

打回与重做不应该抹除上一次结果，至少要保留轮次信息或版本号。

---

## 4. 顶层分区设计

建议统一按以下 6 个命名空间组织：

```text
task.*
workflow.*
collector.*
analysis.*
report.*
qa.*
```

对应职责：

- `task.*`
  - 任务基础信息与整体状态
- `workflow.*`
  - 路由、轮次、当前节点、澄清状态
- `collector.*`
  - 搜索与抓取结果
- `analysis.*`
  - 结构化分析结果
- `report.*`
  - 报告草稿与最终报告
- `qa.*`
  - 质检结果与打回原因

---

## 5. Key 命名规范

建议统一采用：

```text
task:{taskID}:{scope}:{field}
```

例如：

- `task:123:task:meta`
- `task:123:workflow:state`
- `task:123:collector:sources`
- `task:123:analysis:result`
- `task:123:report:draft`
- `task:123:qa:result`

优点：

- 便于 Redis 查询
- 便于按任务清理
- 便于追踪某一阶段的数据

## 6. 字段清单

## 6.1 `task.*`

### `task:meta`

建议包含：

- `id`
- `title`
- `competitors`
- `dimensions`
- `createdAt`
- `updatedAt`

建议包含：

- `status`
- `progress`

- `status` 对齐 `domain.TaskStatus`
- `progress` 由 workflow engine 统一维护

## 6.6 `qa.*`

### `qa:result`

建议包含：

- `score`
- `result`
- `issues`
- `targetAgent`
- `reason`

建议保存每一轮 QA 结论：

- `round`
- `score`
- `result`
- `issues`

这部分对后续 Trace 回放和打回可视化很有用。

## 7. 字段 ownership 规则

建议明确“谁写什么”：

| 分区 | 主写入者 |
|---|---|
| `task.*` | workflow engine / task service |
| `workflow.*` | coordinator / router |
| `collector.*` | collector |
| `analysis.*` | analyst |
| `report.*` | writer |
| `qa.*` | qa |

约束：

1. Agent 只能主写自己负责的命名空间
2. 公共状态由 workflow engine 更新
3. Router 只写路由与重做相关字段

## 8. Blackboard 接口建议

建议在 `internal/state/blackboard.go` 定义：

```go
type Blackboard interface {
    Put(ctx context.Context, key string, value any) error
    Get(ctx context.Context, key string, dest any) error
    Delete(ctx context.Context, key string) error
    ListByPrefix(ctx context.Context, prefix string) ([]string, error)
}
```

在此基础上再封装语义化方法：

```go
type TaskBlackboard interface {
    SaveTaskMeta(ctx context.Context, taskID string, meta TaskMeta) error
    LoadTaskMeta(ctx context.Context, taskID string) (TaskMeta, error)

    SaveWorkflowState(ctx context.Context, taskID string, state WorkflowState) error
    LoadWorkflowState(ctx context.Context, taskID string) (WorkflowState, error)

    SaveCollectorOutput(ctx context.Context, taskID string, out CollectorOutput) error
    LoadCollectorOutput(ctx context.Context, taskID string) (CollectorOutput, error)

    SaveAnalysisOutput(ctx context.Context, taskID string, out AnalysisOutput) error
    LoadAnalysisOutput(ctx context.Context, taskID string) (AnalysisOutput, error)

    SaveReportDraft(ctx context.Context, taskID string, draft ReportDraft) error
    LoadReportDraft(ctx context.Context, taskID string) (ReportDraft, error)

    SaveQAResult(ctx context.Context, taskID string, result QAResult) error
    LoadQAResult(ctx context.Context, taskID string) (QAResult, error)
}
```

这样做的好处是：

- 底层可以换 Redis 或内存
- 上层不直接操作字符串 key

## 9. 轮次与版本管理

QA 打回后，Blackboard 不能只保留最新值。

建议至少支持两种方式之一：

### 方案 A：版本字段

每个结构包含：

- `round`
- `version`

### 方案 B：版本化 Key

例如：

- `task:123:analysis:result:v1`
- `task:123:analysis:result:v2`

推荐做法：

- 对外读取“当前版本”走固定 key
- 历史版本放在 `history` 或版本化 key 中

---

## 10. 与 MySQL 的关系

Blackboard 不是最终展示层数据库。

### Blackboard 负责

- 中间态
- 运行态
- 重做态
- 流程协作数据

### MySQL 负责

- 最终 `Task`
- 最终 `Report`
- 最终 `Trace`

也就是说：

- 多 Agent 运行时主要读写 Blackboard
- 流程结束后再将结果沉淀到 MySQL

---

## 11. 与现有仓库的映射关系

当前仓库已有：

- `internal/domain/analysis.go`
- `internal/repository/analysis.go`
- `TaskEntity / ReportEntity / TraceEntity`

建议映射：

| Blackboard | 现有落库对象 |
|---|---|
| `task:meta` | `domain.Task` |
| `collector:sources` | `domain.Report.Sources` 的来源基础 |
| `analysis:result` | `domain.Report` 的中间数据 |
| `report:final` | `domain.Report` |
| `qa:result` | `domain.Report.QAScore` + `Trace` 元数据 |

## 13. 风险与控制

### 风险一：字段散乱

对策：

- 所有字段必须归属到 6 个固定分区

### 风险二：多个 Agent 同时改同一字段

对策：

- 明确 ownership
- 公共状态统一由 workflow engine 写

### 风险三：重做覆盖历史

对策：

- 引入 `round` / `history`

---

## 14. 本文档产出的直接结论

实现时应保证：

1. Blackboard 是多 Agent 协作中心
2. Key 命名统一为 `task:{taskID}:{scope}:{field}`
3. 所有阶段数据都分区保存
4. 字段 ownership 清晰
5. QA 打回后要保留轮次与历史
